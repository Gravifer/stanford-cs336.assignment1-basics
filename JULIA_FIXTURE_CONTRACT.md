# Cross-language fixture contract

The existing `tests/_snapshots/*.npz` files store expected outputs only. They prove that Julia can read NumPy transport files, but they are insufficient to execute parity tests independently:

- numerical inputs are regenerated by PyTorch fixtures with `torch.manual_seed(1)` through `torch.manual_seed(6)`;
- model parameters are loaded from the Python/PyTorch-specific `tests/fixtures/ts_tests/model.pt` checkpoint;
- masks, token IDs, positions, configuration, and expected gradients are not bundled with the output snapshots;
- Julia and PyTorch RNGs are not expected to produce identical tensors from the same numeric seed.

Therefore Julia parity must use self-contained, language-neutral fixture bundles rather than reverse-engineering Python RNG streams or loading a pickle/PyTorch checkpoint at test time.

## Bundle location and format

Place generated bundles under `tests/fixtures/julia_parity/v1/`. Each operation owns one `.npz` data file and one JSON metadata file with the same stem. Do not replace the existing Python snapshots until both suites deliberately adopt the new contract.

Metadata must validate against `tests/fixtures/julia_parity/schema-v1.json`, which uses JSON Schema Draft 2020-12. The schema validates document structure; consumers must additionally enforce cross-file invariants such as NPZ key equality, `length(shape) == length(axes)`, actual dtype/shape agreement, and gradient-presence consistency. The test-only Julia consumer in `CS336.jl/test/fixture_contract.jl` performs those checks; its synthetic temporary-bundle tests validate transport and rejection behavior, not Python-to-Julia numerical parity.

NPZ contents must be ordinary numeric or boolean arrays. Object arrays and pickled payloads are forbidden. JSON contains scalar and structural metadata that should not be encoded as zero-dimensional arrays.

## Required metadata

Every JSON sidecar records:

- contract version (`1` initially);
- source Git commit and fixture-generation timestamp;
- operation/adaptor name;
- producer runtime and package versions;
- logical axis names for every array;
- dtype and logical shape for every array;
- scalar hyperparameters and mode flags;
- comparison tolerances used by the Python test;
- whether gradients are present and what scalar objective seeded backward;
- notes for masks, causal behavior, repeated token IDs, tied parameters, or state.

The source commit is provenance, not an instruction to make fixture generation depend on the current working tree.

## Required array roles

Use descriptive stable keys rather than a single `array` key:

- all operation inputs, including masks, indices, and positions;
- every parameter used by the operation, in the producer's documented logical layout;
- expected forward output;
- expected input gradients for differentiable floating inputs;
- expected parameter gradients;
- expected updated parameters and optimizer state for multi-step optimizer fixtures;
- non-trainable input state and expected output state for stateful layers.

Keys follow a dotted logical namespace such as `input.x`, `parameter.weight`, `expected.output`, or `expected.gradient.parameter.weight`. The Julia loader must reject unknown or missing required roles rather than silently ignoring them.

## Layout and indexing boundary

Arrays are stored in the Python/course logical order used by the adapters. For transformer activations this is normally `(batch, sequence, feature)`. Metadata names the axes; shape alone is not treated as sufficient.

Julia fixture adapters perform the one explicit conversion to the package's canonical `(feature, sequence, batch)` internal layout. External token IDs remain zero-based values and are converted to one-based array indices only at lookup. Parameter mappings are operation-specific and tested; a blanket axis reversal is forbidden.

## Gradient rules

A forward-only snapshot does not establish AD parity. Gradient bundles must identify the scalar objective or upstream cotangent used to seed reverse mode. They must include physical representation metadata when representation is part of the experiment.

Embedding baseline fixtures use dense weight gradients because the current course path is dense. A later sparse experiment needs a separate contract containing selected rows, repeated-ID coalescing, sparse layout, optimizer semantics, and untouched-row weight-decay behavior.

## Validation sequence

1. Validate the JSON schema version, array key set, dtypes, shapes, and named axes.
2. Validate all array payloads are non-object, finite where the operation requires finiteness, and within declared domain constraints.
3. Convert layouts explicitly at the boundary.
4. Run Julia forward and compare to the bundled expected output.
5. Run the selected Julia AD backend and compare all declared gradients.
6. Only after correctness passes, admit the case to the benchmark suite.

The Python producer and Julia consumer must both validate the same metadata contract. These are maintainer parity artifacts only; they are not grading adapters or a starter harness for a Julia course.
